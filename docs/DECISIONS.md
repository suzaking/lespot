## 3. 暫定設計判断

| ID | 推奨案 | 代替・メリット／デメリット | 再評価条件 |
| --- | --- | --- | --- |
| D-01 | SvelteKit + TypeScript、Cloudflare Workers/D1/R2 | React系も可能だが小規模SSR/APIを統合。依存・adapter互換性は実装時に確認 | 技術選好の指定、互換性試験不合格 |
| D-02 | Leaflet + 地理院の淡色地図、標準地図切替 | 必須APIキー・地図従量課金を避ける。商業POIや背景の見やすさは商用地図に劣る可能性 | 現地・スマートフォンUXで背景判読が不十分 |
| D-03 | 地域データを取得しブラウザ内で距離・条件検索 | GPSを自サービスへ送らず、API呼出を減らす。大地域ではpayloadが増える | 1地域500件、1.5MB、取得8地域、性能上限 |
| D-04 | 管理者はGit JSON + 検証・公開CLI | 管理UI/Authの実装が不要。非技術者には負担 | 入力担当がGitを扱えない、更新量増加 |
| D-05 | 事実を項目別確認、期限切れは厳密検索から除外 | 誤った肯定を防止。データが少ない時は0件が増える | 根拠を維持したUX改善が必要 |
| D-06 | 1スポット=独立した休憩区画 | 施設全体の条件混同を防ぐ。登録・写真の工数増 | 重複整理・施設内表示を拡張 |
| D-07 | 料金上限は一般成人・予約なし・税込の最低利用料金 | 全施設を時間単価へ無理に換算しない。滞在総額の比較はできない | 料金計算機への明示要求 |
| D-08 | 位置はメモリのみ、外部経路へ出発地を付加しない | プライバシー優先。再読込後に再取得・中心指定が必要 | 永続位置・履歴を求める新要件 |
| D-09 | 初期60件・無料20件・屋内20件・写真付き40件 | 小範囲で質を担保。写真許可・現地確認の工数が必要 | 実地調査で達成困難なら範囲・数値を承認変更 |
| D-10 | 閲覧アカウントなし、広告・解析SDKなし | 低コスト・小さい個人情報リスク。継続率等を直接測れない | 投稿・収益化・分析を追加する時 |
